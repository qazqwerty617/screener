# Безопасная эксплуатация платежей

Платёжный контур работает по принципу fail-closed: метод появляется в интерфейсе только при наличии его серверной конфигурации. Автоматически поддерживаются только Crypto Pay и USDT TRC-20. BEP-20, ERC-20 и Aptos отключены, пока для них не появится полноценная серверная проверка сети, контракта, суммы, времени и финальности транзакции.

## Обязательные действия перед запуском

1. Отозвать и перевыпустить все ранее записанные в исходниках Telegram-токены. Старые токены считаются скомпрометированными.
2. Создать отдельное приложение Crypto Pay через `@CryptoBot → Crypto Pay → Create App`. Не использовать токен обычного Telegram-бота вместо API-токена Crypto Pay.
3. Сохранить значения из `.env.example` в менеджере секретов хостинга. Не коммитить заполненный `.env`.
4. Указать Crypto Pay webhook только по HTTPS:

   `https://ВАШ-ДОМЕН/api/pay/webhook/cryptobot/<CRYPTO_PAY_WEBHOOK_SECRET>`

5. Сначала провести тестовые платежи с `CRYPTO_PAY_TESTNET=true`, затем создать отдельный mainnet-токен и переключить значение на `false`.
6. Ограничить исходящие права Crypto Pay приложения: функция переводов пользователям системе приёма платежей не нужна и должна оставаться выключенной.
7. Настроить резервные копии `payments.json`, `payment_invoices.json` и `users.json` с шифрованием и ограниченным доступом.
8. Сменить ранее открытый SSH-пароль сервера, запретить вход `root` по SSH и использовать для `deploy.js` отдельный непривилегированный аккаунт с приватным ключом и закреплённым fingerprint хоста.

## Гарантии реализации

- webhook без секретного URL и корректной HMAC-подписи отклоняется;
- перед выдачей подписки Crypto Pay повторно опрашивается сервером, а ID, статус, payload, актив и сумма сверяются с сохранённым инвойсом;
- TRC-20 принимает только подтверждённый перевод точного количества токенов официального USDT-контракта в допустимом временном окне;
- цена и длительность тарифа берутся только из серверной таблицы;
- статус инвойса доступен только его владельцу;
- повторные webhook и перезапуски не добавляют подписку второй раз;
- инвойсы и платежи записываются через временный файл, `fsync` и атомарное переименование;
- секреты не имеют значений по умолчанию, а ошибки сервера не раскрываются клиенту.

## Ограничения

Файловое хранилище рассчитано на один процесс Node.js. Перед горизонтальным масштабированием нужно перенести платежи, инвойсы и idempotency-ключи в транзакционную БД с уникальными индексами по `invoiceId` и `txId`. TLS, WAF/DDoS-защита, резервное копирование, мониторинг и ротация секретов настраиваются на инфраструктурном уровне и не могут быть гарантированы одним исходным кодом.

Если репозиторий когда-либо отправлялся на удалённый сервер, после ротации секретов удалите их из истории специализированным инструментом и попросите всех участников заново клонировать очищенный репозиторий.
